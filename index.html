Workflow

From exported JSON to requests you can verify, in four steps.

Keep a trace back to the source collection while deciding how the generated requests should run.

01

Select inputs

Choose a v2.0 or v2.1 collection JSON, plus environment and globals when needed. v2.0 is normalized in memory; the source file stays unchanged.

02

Analyze

Inspect convertible requests, blockers, scripts, and the variable dependency graph. This step does not call your API.

03

Choose a strategy

Keep collection order, split independent requests, or export only a report. The preview explains why a request needs an ordered run.

04

Export and verify

Run scenario.http from the first request. Run independent.http requests separately. Compare runtime behavior when parity matters.

Capabilities

A careful migration with enough context to keep working.

↗

Independent requests stay independent

The dependency graph separates stand-alone requests from steps that consume earlier values. You can also preserve full order or produce only a report.

◈

Environments and scripts

Mapped variable scopes and reviewed pm.* APIs are carried over. Sensitive values go into a private environment listed in .gitignore.

⌘

No silent downgrade

GraphQL, gRPC, and WebSocket are emitted only with sufficient metadata. Anything whose semantics cannot be preserved is listed in manual-review.md with a source pointer.

◎

Differential comparison

Newman and IntelliJ trace adapters compare method, URL, headers, body, status, and assertions. Sensitive values are redacted with fingerprints.

▣

Built into the IDE

Open Tools → Postman Migration Assistant or press Ctrl+Alt+Shift+P. Preview, dependency graph, output, and report stay in one workflow.

◇

Offline analysis

Collection reading, analysis, and export happen locally. The import workflow does not call Postman, JetBrains, or a developer backend.

Clear boundaries

Unsupported JavaScript, complex network or async behavior, and incomplete protocol metadata may need manual work. A convertible request is not proof it ran correctly against your API. Compatibility is stated only for the tested target in the compatibility matrix ↗.

Frequently asked questions

Short answers for a clear decision.

What does this plugin do?

Postman Migration Assistant analyzes Postman Collection v2.0/v2.1 and exports IntelliJ HTTP Client requests, environment files, compatible scripts, a source map, and a report of items needing review.

Do I need to export my v2.0 collection again?

No. The plugin accepts v2.0 and v2.1. It normalizes v2.0 in memory without modifying the source file.

Why must some requests run from the beginning?

Requests in scenario.http may use a token, ID, or variable produced earlier. Run them in order. Requests in independent.http can run separately or in parallel.

Does 97.2% mean requests succeed at runtime?

No. It is static conversion coverage: 2,510 of 2,582 executable requests in 20 public collections. Runtime testing against the target API is still required.

Is my collection uploaded to a server?

No, not during import. Analysis and export run locally. When you execute a generated .http file, IntelliJ HTTP Client sends requests to the API you configured.

Does it support GraphQL, gRPC, and WebSocket?

Conditionally. GraphQL needs a query; gRPC needs a URL, service/method, and message; WebSocket needs a URL and message sequence. Incomplete requests are flagged for manual review.

What is included in Free and Pro?

Free analyzes the full collection and exports safe independent basic requests. Pro preserves supported scripts, dependent scenarios, advanced OAuth2 and HTTP runtime semantics, and adds differential verification. Unsupported behavior remains manual review in both.

Which IDE is currently targeted?

Version 1.0 targets IntelliJ IDEA Ultimate 2025.3.2 (IU-253.30387.90). Check the compatibility matrix for current evidence. Broader IDE and operating-system support has not been announced.
